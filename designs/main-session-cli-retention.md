# 主会话 CLI 保留策略设计

日期：2026-09-08，状态更新：2026-09-09。GPT-5.6 Sol 已完成设计、实现与多轮修正审计；设置样式已经用户确认并落地，最终独立终审结论为 `PASS`。本地真实 Chromium 已验证桌面与移动尺寸、明暗主题、legacy 首次接管预填 60 分钟/10 个/归档关闭开启，以及对应 PUT 请求。真实 Host/CLI runtime、部署和跨平台代表路径仍未验收，完成前禁止发布。

源码调查以 `7e5f92fe0` 加当前工作区实际字节为依据；工作区已有大量相关未提交修改，实施必须保留无关字节。本设计经独立 Codex 与 Claude 设计审计。后端候选已加入持久关闭意图、按 archive scope 隔离的 Runner generation fence、Host 数据库租约、跨副本重试及安全 reset；审计不替代运行时验收。

## 目标与使用路径

用户配置“空闲认定时间”和“空闲 CLI 保留上限”。例如 Claude 设置 60 分钟、10 个：连续无实际工作满 60 分钟的主会话 CLI 才进入空闲池；池内超过 10 个时，关闭其中最久未活动的 CLI。达到时间门槛本身不触发关闭。工作中、受保护、刚结束但未达到门槛的 CLI 都不占这 10 个名额。Codex 独立计数，subagent 不单独计数。

另有独立开关“归档时立即关闭 CLI”：开启时归档立即启动该会话的停止与清理，不等时间门槛、不看空闲池额度。关闭时归档只改变归档状态，CLI 继续按空闲池规则管理。会话记录及工作目录保留；取消归档不自动启动 CLI，再次发送消息时才恢复。

要求来源：用户明确纠正“允许的空闲 CLI 上限，空闲 1h 才计数，活动 CLI 不占数”，认可最老的排序定义，随后要求归档立即关闭且可开关，并要求更新文档、后续审计和落地都交给 5.6。原稿中“两种独立淘汰条件”“总存活数软/硬上限”“全忙时排队还是超限”的设计已被此口径取代。数量规则按 Host 分池，同一组参数按实际 CLI 家族分别计数；首期不提供每家族不同参数。

## 产品语义

### 1. 时间是连续空闲时间

名称用“空闲认定时间”，单位分钟。它只决定什么时候入池，不是最长寿命、执行超时或到期必关。

- 从本轮工作完成、最后一个保护条件解除时开始计时；达到门槛前属于未入池的静置 CLI，达到后才计数。
- 新请求、实际终端输入、恢复执行、子任务活动使会话受保护，完成后重新计时。
- 浏览聊天历史、切换侧栏、置顶、SSE/WS 心跳、状态查询、后台标题更新不刷新主会话空闲时钟。
- 真正连接原生终端的用户保留现有保护；仅打开普通聊天页不构成保护。断开终端后重新开始空闲窗口。
- “等待”必须分语义：仍有审批/工具问题/恢复中的操作为受保护；一轮已结束后等待下一条普通聊天消息为空闲。
- PTY 输出保留为防误杀信号，不能简单删除。现有近期输出保护窗为 120 秒，因此门槛设为 1 分钟时，真实入池可能晚于 1 分钟；UI 说明保护活动会延后入池。若无法区分背景刷新和真实输出，宁可延期并显示原因，不宣称分钟级精确定时。
- 使用 Runner 内单调时钟计算持续时间；跨 Runner 排序不得直接比较不同进程的 monotonic 值。

### 2. 数量只算达到门槛的空闲主会话

一个名额代表一个真实存活、可确认无保护条件、连续静置已达到门槛的主会话 CLI 实例。UI 主计数为“空闲池数量 / 上限”；总存活数只作为补充，另展示工作中、静置未达门槛、受保护、回收中、状态未知。状态未知不得显示为已确认空闲。

- 已创建但还没启动 CLI 的会话、历史列表中的离线会话不占名额。
- 同一主会话的 native pane、harness proxy、app-server、专属 forwarder/MCP 等组成同一个资源集合，达到入池条件后只占一个名额。
- 主会话的 subagent 不单独占名额；不能只依据终端名字是 `main` 来认定主会话。
- 使用明确的会话 lineage：parent 为空、root 指向自身且不是 sub_agent 类型。旧数据/导入身份矛盾时标记未知，不猜测后回收。
- fork 创建新的顶层会话时，是独立运行实例，但也需达到入池条件才占一个名额；只是 subagent transcript 镜像则不占。
- 计数跟 CLI 家族走，不跟模型、API 供应商、自定义 Agent 显示名、CWD 或项目走。同一 Claude CLI 的不同模型仍属于 Claude。
- 首期必须验证 Claude、Codex 的原生及实际使用的 SDK 路径是否持有长期 CLI；持有时归同家族。纯 HTTP/按次运行且不驻留 CLI 的执行方式不凭 UI 名字占名额。
- 家族映射及可回收能力由后端已有 native coding agent/harness 元数据维护；前端不复制映射表，不通过字符串前缀猜 vendor。未适配 harness 显示“不支持自动回收”，不能给出虚假 0。

池键建议为 `(Server workspace/tenant, owner, host_id, cli_family)`。同一 Host 跨多个 Runner、多个项目合计；不同 Host 各自算。不同 Server 的同一物理机器不承诺统一额度。无 Host 绑定的外部 Runner 不伪装成某台 Host，首期显示不支持数量管理。

### 3. 时间门槛和数量上限串联

规则只有一条：连续无工作达到门槛 → 入空闲池 → 池子超额 → 淘汰最老者。未超额时，即使空闲几天也保留。不存在独立的“到点就回收”分支。

UI 提供空闲认定分钟、空闲池保留个数及独立的归档关闭开关。数量可选“不限制”，表示停用空闲池自动淘汰，分钟值仍保留；不能单独关闭分钟门槛而变成所有静置 CLI 立即参与计数。分钟 1–10080，数量 0–100；`max_idle_clis: null` 表示不限制，0 表示达到门槛后一个空闲 CLI 也不保留。拒绝 bool、小数、NaN、负数和超范围值。首期不扩展“完成即关闭”模式。

首次显式启用新空闲池管理时预填 60 分钟、10 个；历史 Host 不自动启用空闲池。每个 Host 只保存一组门槛与上限，按 CLI 家族形成多个独立池。归档开关为 Host 级三态兼容字段：无策略/旧客户端等同 legacy `true`，只有显式 `false` 禁用，显式 `true` 使用完整资源释放。Hostless 会话不受某台 Host 设置控制，首期保留 legacy 归档关闭行为并在 UI 说明。

### 4. 入池、出池示例

Claude 设置 60 分钟、10 个：

1. 5 个工作中 + 4 个静置 20 分钟 + 10 个静置超过 60 分钟：共 19 个 CLI，空闲池为 10/10，不关闭任何一个。
2. 再启动一个工作中的 CLI：共 20 个，空闲池仍为 10/10，不触发淘汰。
3. 一个静置实例达到 60 分钟，空闲池变成 11/10：回收池中最久未工作的一个，收敛到 10/10。
4. 池中某个 CLI 开始工作：立即出池，不再占名额；工作完成后从零计时，满 60 分钟再入池。
5. 一个任务刚结束，即使池中已有 10 个也不能回收它；它还没达到入池门槛。

总存活数不受这 10 个限制。不存在“工作中导致暂时超限”的产品状态，也不引入启动排队；空闲池在上报/清理期间短暂超过额度时显示“正在回收”，不能与活动 CLI 数量混淆。

### 5. 淘汰规则

只从已达到时间门槛且可确认无保护条件的运行实例中按 `idle_since` 从早到晚选择；并列用稳定主会话 ID 排序。创建时间、最后修改标题、最后浏览时间、置顶、未读不参加排序。

设 E 为达到门槛的真实存活实例数（含其中已领取且正在清理的实例），N 为上限，R 为 E 中具有有效回收意图的不同实例数，本轮最多再领取 `max(0, E - N - R)` 个最老候选。不得先清空所有达到门槛的实例。实例结束并核实资源退出前，UI 不把回收中当成已释放。候选变忙/失去入池资格则跳过并重算，不沿用旧缺口和快照连续淘汰。

### 6. 归档立即关闭开关

- **开启**：用户成功归档后立即提交停止与关闭操作，不等待入池或额度判断。运行中、审批中、尚未达到空闲门槛也会停止；归档交互旁要明确这一影响，不静默等待其自然结束。
- **关闭**：归档只管理会话可见性；已经开始的任务及其为完成本轮工作所需的子任务继续运行，CLI 继续空闲池生命周期。归档状态本身不刷新活动时间。
- 归档会话对新的用户输入保持只读：message、新 turn、retry、compact 等会启动/唤醒工作的外部动作返回 409，提示先取消归档；Runner 回传的状态、结果和必要收尾事件仍允许。开关关闭时，这个只读门禁不能阻断归档前已经在跑的任务继续派生和接收子任务结果。
- 开关开启时，归档提交与一个有效的 archive close intent 原子关联。该 intent 立即阻止根会话及子树启动新工作或自动唤醒，随后取消现有工作、处理审批/待交付结果并释放资源。停止范围以持久化 `parent_conversation_id` / `root_conversation_id` 枚举，不以 best-effort 状态缓存决定是否尝试停止；未知状态也逐会话执行有代次保护的释放。共享服务、其他主会话、工作目录和历史记录不删除。
- “立即”指归档提交后立即开始有界的优雅停止与清理，不是承诺零耗时强杀。UI 分开显示归档成功与 CLI 关闭中/已关闭/关闭失败。Host 离线时显示待关闭，重连后再执行，不能声称离线进程已经停止。
- 取消归档不会自动开 CLI。取消归档使尚未进入资源清理临界区的 close intent 失效；若已经进入清理，则等待该代清理完成。之后用户主动发送消息才恢复。不能在仍有效的归档关闭意图下后台偷启新 CLI。
- 归档版本与运行 generation 一同绑定关闭意图。归档之后取消归档、又启动了新代 CLI，晚到的旧归档请求不能杀新实例。取消归档不撤销已经进入清理临界区的停止，但应允许清理后正常恢复。
- 开关仅作用于其开启时新发生的归档操作；开启时不批量补杀历史已归档会话。关闭开关阻止后续归档产生关闭意图，不撤销之前已提交的归档关闭请求。单条、批量、API 归档使用同一后台逻辑；批量结果逐会话可见，失败不伪装全部成功。
- 空闲池保护条件只约束自动淘汰；显式归档停止走独立原因 `archive`。两者共用 Runner 所有的、状态无关且幂等的 `release_session_resources(reason, runtime_generation)` 资源边界；空闲池调用前必须满足 busy/门槛/代次复查，归档调用先取消工作后强制释放。这个资源边界关闭对应 pane、harness subprocess、forwarder/app-server、session router 和专属辅助资源；Host 专属 Runner 再走现有 `host.stop_runner`。不得只给 `_spawn_archive_stop` 加开关，也不得为归档放松空闲池的 busy 保护。

建议：设置 → 运行与资源 → 空闲 CLI 保留。顶部选择已登记的 Host，显示连接情况；无 Host 时展示说明，不显示假在线列表。

空闲 CLI 保留上限  [10] 个 / agent（可选不限制）
[✓] 归档时立即关闭 CLI（会停止该会话正在运行的任务）

Agent             空闲池         状态

- 同页可展开某个 agent 查看主会话、工作/保护原因、空闲时长、最近回收原因；首期不另建进程管理控制台。
- Agent 行只展示按同一规则分别计算的空闲池和能力状态；首期没有每家族不同的配置表单。
- 编辑不立即回收，只有保存才提交。保存前内联显示基于当前快照的预计影响，如“按当前状态预计回收 3 个空闲会话”；这是动态估计，真正执行仍二次核实，不承诺固定名单。
- 保存结果区分“已保存”“已应用”“部分实例尚未应用/版本不支持”“Host 离线，待应用”，不能保存数据库成功就写成已生效。
- 空闲池规则修改作用于现有及新实例。调整分钟后按原 idle_since 重新分类，不从保存时重新计时；降低门槛会使更多实例入池，但仅超额才回收，提高门槛可使部分实例退出计数。提高个数或设为不限制不主动启动已关闭 CLI。归档开关只影响后续归档事件。
- 空闲池回收显示“CLI 已休眠 · 空闲池超额；发送消息继续”，不改变会话业务状态为失败、完成或归档，不发任务完成通知。归档关闭显示“已归档 · CLI 已关闭/关闭中/待关闭/失败”，业务归档状态由归档操作持有。
- 每保留一个 Host 启动的空闲 CLI，通常也保留一个专属 Runner、tmux/pane 及相关 MCP 进程。已实现 UI 持续说明资源影响，并对较高或不限制的上限明确强调内存占用。小屏幕将 Agent 行变为紧凑列表；输入可用键盘操作、单位明确，状态不只依赖颜色。可交互样式已经用户确认，实现沿用该布局与信息层级。

## 技术边界与所有权

采用 Server 保存策略并跨 Runner 协调空闲池数量、Runner 持有真实运行实例和最终回收权。归档事件由 Server 生成单独的关闭意图，复用取消/停止和按会话资源清理机制。复用现有 Runner HTTP/tunnel 传输；不增加通用进程扫描 daemon，不按进程名 kill，不由浏览器定时器执行。

Host daemon 保持在线；Server 历史和工作目录不删除。Server 聚合是协调投影，不取代 Runner 的真实生命周期。历史 `session.status` 只能辅助展示。

### 策略持久化和接口

新增独立的 Host 策略子资源（建议 `/v1/hosts/{host_id}/cli-retention`），避免改变现有 Host PATCH 的 default_workspace 语义。复用 HostStore/SqlHost 所有权边界，增加 versioned 策略存储；不是 `localStorage` 或用户 web preferences。

已实现 GET 返回 `contract_version`、`configured`、`policy`、`revision`、结构化 `application` 与当前副本的 `runtime` 投影；PUT 替换完整策略并携带 `expected_revision`，冲突返回 409，非法输入 422，不属于用户的 Host 遵循现有 403/404 约定。`application.status` 区分 legacy、待应用、Host 离线、其他副本、Runner 不支持、部分支持、状态未知及已应用，并携带策略 revision 与观测时间。严格拒绝未知字段，不丢弃新版本字段再静默保存。

策略形状（字段类型示意）：`{version: 1, idle_threshold_minutes: integer, max_idle_clis: integer|null, close_on_archive: boolean}`。同一规则由 Server 按 `cli_family` 分池应用。revision 是 Server 生成的并发版本。不要沿用旧稿 `max_alive`、`idle_minutes` 或 `overrides` 字段，以免消费者继续按总存活数、独立 TTL 或未确认的每家族设置理解；旧稿尚未实施，无需数据迁移。

Runner 的策略更新与释放接口为内部接口，沿用已有身份和绑定权限。空闲池请求绑定 `session_id + runner_id + runtime_generation + policy_revision + expected_activity_epoch + reason=idle_pool_overflow`；归档请求另绑定 archive_revision，reason=archive，允许执行取消工作但不能忽略 generation/归档版本核实。响应区分 released / already_absent / busy / stale_generation / stale_policy / stale_archive / failed。禁止客户端直接指定任意 PID。归档事件的写入与待关闭意图必须原子持久化或有可靠补偿，避免 Server 崩溃造成“已归档但永不关闭”。当前 `_best_effort_stop` 只作快速取消辅助，不能充当资源释放的成功凭据。

### 生命周期快照

每个可管理主实例至少提供：会话/root/Host/family 身份、运行代次、状态（starting/busy/quiescent/reclaiming/absent/unknown）、活动代次、连续无工作时长、保护原因、已应用策略 revision、上报序号。quiescent 只是当前无工作；是否入池由时长与当前策略计算，不再持久化第二个可写的 pooled 布尔值。

Runner 在工作起止、资源启动/退出、审批/子任务/终端连接变更时上报，并在连续无工作达到门槛时触发一次入池重评；复用现有传输，断线重连发送完整快照。心跳/健康探测不增加 activity_epoch。Server 使用接收时间结合报告的 idle duration 推算排序时间，拒绝旧 generation/sequence，不拿远程 wall clock 直接排序。跨 Runner 最接近的同时刻空闲允许观测精度内并列。

保护谓词必须收敛到 Runner 的一处会话运行状态判断，供入池判定、空闲池回收和 Runner 自动退出共同使用。至少包括：active turn、native 自主运行、pending approval/elicitation、活动工具、未交付结果/正在恢复、依赖的活动子 agent、连接的原生终端、近期有意义输出、状态未知。显式归档停止复用身份校验，但不被“正在工作”无限延期。

子 agent 不能只依靠主会话 UI 标记判断：同 Runner 的任务/定时器/邮箱/唤醒状态从实际容器收集；跨 Runner 的子任务由 Server 补充保护依赖，主 CLI 涉及尚未交付结果时不参与空闲池回收。子 agent 完成且结果已持久化并完成必要交付后，根会话才解除该保护。空闲池规则不按名额杀整棵子任务树；归档关闭则明确停止归档根会话所属子任务，两个关闭原因分开执行。

### 原子回收与恢复

空闲池回收在处理输入/turn 启动所用的同一生命周期互斥边界内，验证身份代次、活动代次、策略 revision、保护谓词及当前持续时间仍达到门槛，再从 quiescent 原子转为 reclaiming。该状态禁止把新输入投递到旧 CLI。耗时资源关闭不持有全局池锁。归档路径先持久化归档与 close intent、阻止新工作，按持久化 lineage 枚举根及全部后代，逐个取消现有工作并进入同一资源清理流程；状态缓存只用于决定可跳过的快速取消，不能让缓存缺失的后代逃过释放。其输入竞争遵守归档/取消归档契约，不能套用自动恢复把归档立即撤销。

- 空闲池回收与输入竞争，输入先获锁：标记 busy/增加活动代次，旧池回收请求失效。
- 空闲池回收先获锁：后续输入沿用原消息 ID 和已有消息持久化路径，等待旧代清理后单次启动新代；不能双发、丢消息或并发 resume 两个 CLI。归档停止不自动执行这个恢复分支。
- 复用按会话资源归属的关闭路径，包含专属 CLI、forwarder/app-server 等。共享 MCP/Host/其他会话或用户终端不误关。退出超时只升级处理已确认属于该代实例的资源，不能裸用复用风险的 PID。
- 部分清理失败保留 reclaiming/failed 及残余资源信息，重试幂等，计数不提前减一；未知状态不作为可淘汰对象。
- 重新发消息先尝试当前 harness 支持的原生 resume，保留 external session ID 与 OSEnv；失败明确提示恢复问题，不静默新建丢上下文会话。没有验证 resume 的 harness 不启用自动回收能力。

### 统一旧的三层回收

显式新策略对纳入管理的主实例取消旧独立 TTL 淘汰权；旧 harness/pane 两个 reaper 不得因 3600 秒或新时间门槛到期就关闭这些实例。时间只用于认定入池，关闭必须来自空闲池超额的条件请求、显式归档停止或其他已有显式停止/故障处理。未纳入的后台/子 agent 资源继续现有规则。

Runner 自动退出前，除现有工具/审批/定时器保护外，还必须检查是否存在应保留的主 CLI。静置未达到门槛、空闲池内未获超额回收决定、设为不限制的主 CLI 都不能被 Runner 的旧空闲超时抢先关闭。主 CLI 已安全释放、其他资源无保护需求时，Runner 可继续其基础设施空闲退出逻辑；不为省 Runner 内存擅自关闭用户终端或共享资源。

兼容采用显式接管：没有新空闲池策略的 Host 保持旧回收配置；归档字段缺失继续等同 `close_on_archive=true`，保持当前必停默认。第一次开启空闲池管理时 UI 展示读到的旧三层有效值；若不一致显示“现有分层规则”，不能伪造为一个统一值。保存时明确“将替换主会话的旧定时关闭规则；时间改为入池门槛”。新策略优先于这些旧环境变量，但只限被管理的主实例。不能把旧独立回收秒数无提示转换为已启用的新池策略。

升级能力不足的 Runner 继续旧行为，并显示未应用；不能承诺混合版本 Host 全部受控。按新策略设置的会话必须确认 Runner 已获得策略才能标记已应用。策略接管后断网不得偷偷恢复 60 分钟默认。发布顺序允许 Server 先具备存储/UI，但 Host 与 Runner 都报告能力前不能启用或显示“已应用”。

### 调度、断线与多副本

- Runner 本地持续测量无工作时长并识别时间门槛；到点只上报，不自行按时间关闭。浏览器关闭不影响 Server/Runner 管理。
- 数量协调由 Server 按池执行：达到入池门槛、活动恢复导致出池、资源退出、策略变更、重连快照到达触发重评；后台约 30 秒一次核对作为漏事件兜底，不能全量扫描历史会话。
- 新实例启动不预留空闲池名额，也不以其启动为由淘汰旧 CLI；只在真实池子超额时回收，不能阻塞新工作。任意时刻重新评估都须使用该时刻的有效池成员数。
- Server 到 Runner 状态失联或过期时，数量调整暂停，UI 显示状态未知；绝不把 unknown 算成空闲。重新连接后拿完整新鲜快照再收敛。
- Server 断开期间暂停跨 Runner 空闲池回收，Runner 继续计时但不能到点自行关闭，也不能退回旧 TTL。重连后用新鲜全量快照收敛。归档关闭意图若已可靠交付则可继续执行；尚未交付的保持待关闭，恢复连接后核对归档版本再发送。
- 使用现有按 Host 路由/tunnel 所在副本处理命令，但不能假设它天然防止多副本重复淘汰。每个池使用数据库支持的短事务互斥/版本化领取，记录带代次的进行中回收意图；Postgres 与 SQLite 都必须有契约测试。网络关闭调用在事务外执行。
- 领取时扣除同池有效进行中意图，防止两个副本同时各释放一批而超额淘汰。归档已领取的关闭实例如仍属于 E，也要在 R 去重计入，避免归档与池回收重复释放名额。策略修改/不限制撤销尚未提交到 Runner 的旧池意图；已原子进入 reclaiming 的关闭可完成。归档意图按归档事件和 archive_revision 管理，不被普通池参数修改撤销。
- 回收结果未知时不因简单超时就换另一个候选或重新杀旧 PID；先向当前绑定 Runner核实该代实例。Server 重启后协调状态由持久化意图和 Runner 完整快照恢复。失去协调权的旧执行者不得新发回收命令。

## 方案取舍与自检

采用跨 Runner 的 Server 协调加 Runner 最终条件回收，因为单个 Runner 看不见整个 Host 的空闲池。纯前端方案无法在浏览器关闭后工作；只修改某一个 reaper 不能阻止其他层提前关闭；Host 新建全套本地 IPC 协调会扩大通信面；本需求不包含总存活数限制、独立 TTL 回收或启动排队。

设计交叉审计结论为 `CONDITIONAL / cross-model`；首轮实现审计结论为 `FAIL`，多轮修正后的最终独立终审结论为 `PASS`。已通过测试的候选包括严格 Host 策略/CAS、按 family 分池、统一观测时间轴的最老选择、native pane 与 Windows `codex`/`claude-sdk` resident harness、活动代次复查、归档开关的 legacy 默认、Hostless 归档、关闭时已归档会话继续入池、状态未知后代尝试释放、Host ID 轮换保留策略，以及旧 reaper 最终关闭前复查接管状态。

需要保留的新增状态只有：持久化版本策略、Runner 生命周期与活动代次、Server 可恢复且区分原因的关闭意图；复用归档版本/并发控制，不复制第二份归档真值。运行快照是 Runner 的投影，不成为第二套可写业务会话状态。首期不加固定保活/置顶豁免、内存百分比回收、多层继承、跨 Server 全机配额或独立进程控制台。
